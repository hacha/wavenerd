想定読者：TypeScript / React / Web Audio の基本は分かるが、wavenerd のコードはまだ読んでいないエンジニア（仮定。確かめたいことは付録） 読み終えると：音がどこで作られてどこを通るか、テンポの持ち主は誰か、つまみや状態がどう画面と音に届くかが分かり、変更の入口を選べる 省いたもの：Web Audio・React・Jotai・Strudel そのものの入門、セットアップ手順（README.md / CLAUDE.md にある）、テーマ・録音形式・MIDI learn の内部 所要時間：15〜20 分。急ぐなら 0 → 4 → 6 → 10 節の順で 7 分

1. 3 つのスレッドと 4 つのループ

wavenerd の処理は、メインスレッド・Web Worker・オーディオスレッドの 3 か所で動く。 音を作る仕事（GLSL の描画、Strudel の発音予約）はメインスレッドのループが起点で、実際に鳴らすのはオーディオスレッドという分担になっている。

wavenerd を動かし続けているループは次の 4 つで、それぞれ間隔が違う。図に出ているのは、音を作る上の 2 つ。

ループ 間隔 何をする 場所
updateAudioLoop setTimeout の連鎖（前回の完了を待つ） GLSL の 2 デッキの update()。重ならないようにフラグで守る src/index.tsx
TickNode オーディオスレッドから定期的に届く合図（tick） タブが隠れてタイマーが間引かれても、updateAudio() と、Strudel のスケジューラの tick が予定（50ms）の 1.5 倍以上遅れていれば 1 回進める poke() を呼び、音を途切れさせない src/index.tsx, src/audio/TickProcessor.js

2. GLSL デッキ：シェーダが波形を書く

GLSL デッキの本体は外部パッケージ @0b5vr/wavenerd-deck（0.9.0）にある。 ユーザーが書く mainAudio(time) は、フラグメントシェーダの中で 1 ピクセル = 1 サンプルとして呼ばれる。

根拠：

vec2 out2 = mainAudio(mod(_timeHead + floor(gl_FragCoord.x) * _deltaSample, timeLength));
get __framesPerRender(){return 128*this.__blocksPerRender}
e.readPixels(0,0,r,1,e.RGBA,e.FLOAT,0)
new OffscreenCanvas(4,4)

gl_FragCoord.x がサンプルの番号で、_deltaSample（1 / sampleRate）を掛けて時刻にしている。 1 回の描画は 128 サンプル × 16 ブロック = 2048 サンプルで、描画先は Worker の中の OffscreenCanvas に作った 2048×1 px の浮動小数点テクスチャ。

単位は「ブロック」で、1 ブロック = 128 サンプル（AudioWorklet が 1 回に処理する長さ）。 update() は、書き込み位置が再生位置より latencyBlocks ブロックを超えて先行していれば、何もせずに戻る。 wavenerd はこれを既定の 16 ではなく 32 にしている（src/index.tsx）。

  • 1 回の描画：16 ブロック = 2048 サンプル
  • 先行の上限：32 ブロック = 4096 サンプル = 描画 2 回分。48kHz なら約 85ms

根拠：

latencyBlocks: 32,
if (blockAhead > this.latencyBlocks) {

cue の反映（Mod-R）は、次の小節頭の時刻を __programSwapTime に覚えておく。 小節頭が 2048 サンプルの描画範囲の途中、たとえば 500 サンプル目に来たら、0〜499 を古いプログラムで、500〜2047 を新しいプログラムで描く（scissor で範囲を分けて 2 回描く）。 このため反映はブロックの境目ではなく、サンプル単位で小節頭に揃う。

根拠：

= this.beatManager.time - this.beatManager.bar + this.beatManager.barSeconds;
this.__renderer.render(0, beginNext, uniforms);
this.__renderer.render(beginNext, framesPerRender - beginNext, uniforms);

3. Strudel デッキ：同じ箱に別のエンジン

Strudel デッキ（src/strudel/StrudelDeck.ts）はこのフォークで追加したもので、UI からは GLSL デッキと同じに見える。 共通部分は CodeDeck インターフェイスだけで、エディタやステータスバーはこれしか知らない。

export interface CodeDeck {
  readonly cueStatus: CueStatus;

  /** Compile the code and cue it. */
  compile(code: string): Promise<void>;

  /** Apply the cue at the next bar. */
  applyCue(): void;

  /** Apply the cue immediately. */
  applyCueImmediately(): void;

WavenerdDeck は手を加えずにこの形を満たす。キー操作との対応は Mod-S = compile、Mod-R = applyCue、Shift-Mod-R = applyCueImmediately（src/view/components/DeckEditor.tsx）。

Strudel 側の中身は 3 つの部品に分かれる。

  • 評価：Strudel の repl はコードの評価だけに使う。Strudel 標準のスケジューラ（Cyclist）は起動しない。
  • サイクル：Strudel のパターンの時間単位。wavenerd では 1 サイクル = 1 小節に固定している。
  • スケジュール：自前の StrudelScheduler が 50ms ごとに先読み区間を queryArc 相当で問い合わせ、音ごとに AudioContext の時刻を決めて superdough に渡す。
  • 出力先：superdough は本来 ctx.destination に直接つなぐ。DeckOutputController が出力先をデッキごとのノード（strudelDeckX.output）に差し替える。

設計の理由（superdough を fork しない方法、時刻の換算式）は doc/strudel-integration.md にある。

GLSL / Strudel の切り替え（setDeckMode）では、GLSL デッキを止めずに描画だけを止める（DeckRenderGate）。 GLSL デッキの BeatManager がアプリ全体の時計を兼ねていて、update() の中で時計が進むからだ（次の 4 節）。

4. 時計は 1 つ

テンポ・小節位置・再生 / 停止の持ち主は deckA.beatManager だけ。

deckB は hostDeck: deckA で作られ、beatManager の getter が deckA のものを返す。 Strudel の 2 デッキは StrudelEngine が 1 つだけ持つ DeckClock を共有し、DeckClock は deckA の BeatManager の update イベントを購読して、サイクル（= 1 小節）と AudioContext 時刻を相互に換算する。

根拠：

StrudelEngine.ts:94:    this.clock = new DeckClock(hostDeck);
const strudelEngine = new StrudelEngine({ audio, hostDeck: deckA });

return hostDeckBeatManager;

このため BPM を変えたり巻き戻したりすると、4 つのデッキすべてが同時に従う。デッキごとに BPM を持たせる変更は、この前提を崩す。

5. 音声グラフ

グラフ全体は src/index.tsx で組み立てる。前半（デッキからミキサーの出口まで）と後半（出口からスピーカーまで）に分けて描く。

DeckSourceSwitch は GLSL と Strudel の 2 入力を gain で切り替える（setTargetAtTime、時定数 2ms で素早くクロスフェードし、クリックノイズを避ける）。

根拠：

const FADE_TIME_CONSTANT = 0.002;

MixerChannel の中は gain → EQ → filter → volume の順で、EQ と filter は実装を差し替えられる（MixerEQIsolator / MixerFilterBiquad / MixerFilterGate など）。 master limiter は hardClip（既定。±1 で切る）、lookahead、none から選ぶ。

根拠：

MixerChannel.ts:112:    this.__gainNode.connect(this.__eq.input);
MixerChannel.ts:113:    this.__eq.output.connect(this.__filter.input);
MixerChannel.ts:114:    this.__filter.output.connect(this.__gainNodeOut);
MixerChannel.ts:115:    this.__filter.output.connect(this.__gainNodeOutForAnal);

__gainNodeOut がチャンネルの volume で、__gainNodeOutForAnal（外からは outputForAnal）は volume の手前で分岐している。 つまり、ヘッドホンの cue とアナライザは、フェーダーを下げたチャンネルの音も拾う。

ヘッドホン出力は別の AudioContext や setSinkId ではなく、1 つの出力デバイスのチャンネルを分けて実現している。 AudioDestinationRouter は destination.channelCount を maxChannelCount まで広げ、設定の channelRouting に従って各音源のチャンネルを割り当てる。 既定値の master:0,master:1,cue:0,cue:1 は、出力の 1–2ch に master の L / R、3–4ch に cue の L / R という意味になる。 多チャンネルのオーディオインターフェイスがあれば、マスターとヘッドホンを別の端子に出せる。

根拠：

channelRouting: 'master:0,master:1,cue:0,cue:1',
splitter.connect(this.__merger, channel, i);

router.addSource('master', masterGain);
router.addSource('cue', cueMixer.output);
router.addSource('deckA', sourceSwitchA.output);
router.addSource('deckB', sourceSwitchB.output);

録音（Recorder）は masterGain の後ろから取る。リバーブも master の音量も入った、スピーカーに出る音と同じものが録れる。

6. つまみの値は MIDIManager に集まる

画面のつまみ・フェーダーも MIDI コントローラも、値を直接音声オブジェクトに書かない。 どちらも MIDIManager に書き、paramChange イベントを受けた applyMidiParam（src/index.tsx）が音声側に配る。

根拠：

MIDIMAN.setValue(midiParamName, saturate(v));
if (paramKey === '/deck_a/knob0') { deckA.setParam('knob0', value); }
strudelDeck.setParam(strudelKnob[2], value);
MIDIMAN.on('paramChange', ({ paramKey, value }) => applyMidiParam({ paramKey, value }));

キーは /mixer/channel_a/volume や /deck_a/knob0 のようなパス文字列。 knob0〜knob7 は同じスロットの GLSL デッキと Strudel デッキの両方に送られるので、モードを切り替えても MIDI の割り当てはそのまま使える。 値は midi.json として OPFS に保存される。

7. 状態が画面に届くまで

デッキや MIDIManager は React の外にあるイベントエミッタ（src/utils/EventEmittable.ts）。 画面に届くのは、購読フックがイベントを Jotai の atom に写したときだけで、その atom を読むコンポーネントだけが再描画される。

コンパイルエラーの例では、useDeckSubscribers が error イベントを deckAErrorAtom に書き、DeckStatusBar がそれを読む。

    const handleError = ({ error }: CodeDeckEvents['error']) => {
      setError(error ?? null);
    };
    deck.on('error', handleError);

購読フック（useDeckSubscribers / useMidiSubscribers / useSettingsSubscribers など）の呼び出し元は App だけ。 新しいイベントを画面に出すときは、atom を src/view/stores/atoms/ に足し、購読を src/view/stores/hooks/use*Subscribers.ts に足す。

レベルメーターや波形のように毎フレーム変わるものは、atom を通さない。 FrameEmitter の update を useFrame（または frameEmitter.on）で受け、canvas や DOM を直接書き換える。React の再描画を毎フレーム起こさないための分け方。

11. 理解度チェック

Q1. スロット A を Strudel モードにしても、deckA（GLSL デッキ）の update() が回り続けるのはなぜか。

答え

deckA の BeatManager がアプリ全体の時計で、update() の中で beatManager.update() が呼ばれるから。止めると Strudel デッキも小節位置を失う。描画だけを DeckRenderGate で止めている（3 節・4 節）。

Q2. チャンネル A のフェーダーを 0 にした。ヘッドホンの cue で A を選ぶと、A の音は聞こえるか。

答え

聞こえる。cue は outputForAnal から取り、これは volume（__gainNodeOut）の手前で分岐している（5 節の MixerChannel.ts:115）。

Q3. マスターにディレイを足し、画面に「ディレイ量」のつまみを作った。つまみの onChange で delay.wet.value を直接書けば、画面からは動く。この実装で困ることは何か。

答え

MIDI コントローラから動かせない（MIDI learn の対象にならない）し、値が midi.json に保存されず再読み込みで戻る。つまみは MIDIMAN.setValue で書き、applyMidiParam に 1 行足して音声側に配る（6 節）。

Q4. GLSL デッキで、Mod-R の反映がブロック（128 サンプル）の境目ではなく小節頭ちょうどで起きるのはなぜか。

答え

__programSwapTime に小節頭の時刻を持ち、2048 サンプルの描画範囲の途中から新しいプログラムで描くから（2 節）。

Q5. マスターの現在のピーク値（dB）を数字で表示したい。「deckAErrorAtom と同じように atom を 1 つ足し、FrameEmitter の中で書き込む」案は妥当か。

答え

妥当ではない。毎フレーム atom が変わり、読むコンポーネントが毎フレーム React の再描画を起こす。毎フレーム変わる値は useFrame で受けて DOM のテキストを直接書き換える（7 節）。
